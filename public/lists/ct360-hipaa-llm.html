Read the granularity, not just the yes

Every vendor on this page will say yes to a BAA. They do not all say yes to the same size of thing. AWS publishes "Amazon Bedrock" and "Amazon Bedrock AgentCore" as individual line items on a named eligible services list. Microsoft publishes "Azure and Azure Government", a platform, and keeps the per service appendix behind a sign in. Google publishes an enumerated product list and Vertex AI is not on it.

That is a real difference in what each company is willing to put in writing, and it is the difference that decides whether a compliance table can cite a source. Ask which named service, not whether they sign.

Route by route

What each vendor actually commits to

Anthropic Claude API, HIPAA readiness
Confirmed
What the vendor says
Anthropic will sign a BAA for the first party Claude API. You review and execute it in the Console and enablement takes effect immediately.
Which named service is covered
The Claude API at api.anthropic.com only, and within it only the features marked eligible. Covered: Messages API, token counting, prompt caching, structured outputs, PDFs sent inline, citations, search results, web search, computer use, the bash tool, the text editor tool, the memory tool, thinking, adaptive thinking, effort, fast mode, fine grained tool streaming, mid conversation system messages, data residency, and the one million token context window.
Explicitly excluded
Batch processing, the Files API, code execution, programmatic tool calling, the MCP connector, MCP tunnels, Agent skills, Claude Managed Agents, browser use, web fetch, tool search, the advisor tool, cache diagnostics, context editing, context management and compaction, and Claude Code. Also excluded: the Console itself, consumer plans, Claude Platform on AWS, and Microsoft Foundry.
What that exclusion does and does not mean
This is an API exclusion list, not a fact about the products. Anthropic's retention page scopes itself to the Claude API in a note at the top, so everything above is about this route only. On Claude Enterprise, Anthropic's own BAA article puts Claude Code in the terminal and the Code tab of Claude Desktop at covered, once a Primary Owner activates HIPAA compliance and applies the HIPAA configuration. Still not covered there: the VS Code and JetBrains extensions, and Claude Code reached through Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, an LLM gateway or a custom base URL. Anthropic's words: standard Claude Enterprise plans do not include BAA coverage without action from a Primary Owner.
Three things that decide the architecture
  • It is permanent. Anthropic's words: once enabled, the configuration cannot be disabled by an administrator.
  • It is organization wide. Anthropic's own guidance is to use separate organizations for HIPAA and general purpose work. So CT360 gets its own organization, not the one anything else runs on.
  • Context editing and compaction are not covered. That is the one most likely to bite a long running agent over a patient record, because both are the normal way to handle a conversation that outgrows its window.
The trap in the fine print
With structured outputs, the JSON schema is compiled and cached separately from the message content, for up to 24 hours, and does not receive the same PHI protections. Anthropic's instruction is explicit: do not include PHI in schema property names, enum values, const values or pattern regular expressions. A connector mapper that builds schemas out of real patient fields walks straight into this.
The gap a builder has to know about
As a rule the API returns a 400 error when a request uses a feature that is not eligible, which is the behaviour you want, because a refusal is visible and a silent success is not. There is one documented exception, and it fails the other way. Anthropic's own words on the browser use tool: not covered under HIPAA readiness, requests that include the browser use tool are not blocked. So a request carrying browser use is accepted, it succeeds, it sits outside the BAA, and the developer gets no error to tell them so. Every other feature marked not eligible is blocked with the 400. Browser use is the one to put in a code review checklist, because it is the only one the platform will not catch for you.

Read at platform.claude.com/docs/en/manage-claude/api-and-data-retention, all 35 rows of the feature eligibility table.

AWS Bedrock
Confirmed
What the vendor says
Both Amazon Bedrock and Amazon Bedrock AgentCore appear on the AWS HIPAA eligible services list as their own line items, with no exception attached to either. Coverage is under the existing AWS BAA, so one signature covers Claude, Llama, Mistral and Amazon's own models without negotiating with any model provider separately.
The qualifier that matters
AWS's exact wording is that generally available features of an eligible service are also eligible unless specifically excluded. Read the other way round: a Bedrock feature still in preview is not carried by that sentence. There is no footnote naming a Bedrock exclusion today, so the live question is release state, not a carve out.
Who the processor is
On Bedrock the data processor is AWS, not Anthropic. Anthropic says so itself. Its HIPAA readiness does not reach Bedrock, so the controls to read are Amazon's.

Read at aws.amazon.com/compliance/hipaa-eligible-services-reference.

Azure OpenAI under the Microsoft BAA
BAA yes, service not confirmed
Does Microsoft itself say it signs a BAA
Yes, clearly, and there is nothing to sign. Microsoft's words: there is no separate contract, because the HIPAA BAA is available through the Product Terms by default to every customer who is a covered entity or a business associate. Executing a volume licensing agreement includes executing the HIPAA BAA.
Which named service is covered
Microsoft's in scope list is written at platform granularity. The entry is "Azure and Azure Government". Individual Azure services are not enumerated on it, and Azure OpenAI is not named anywhere on either Microsoft compliance page. The per service appendix lives in a Service Trust Portal document that requires a sign in, so it could not be read.
So what is the honest answer
The BAA is confirmed. "Azure OpenAI is in scope" is not confirmed at a Microsoft compliance page. The only Microsoft hosted text that names Azure OpenAI is the Microsoft Q and A forum, which is not the Product Terms. Compare AWS, which names Bedrock as its own line item: the same question has a published answer there and does not here.
What would settle it
One request through the account's licensing contact for Appendix A of the Microsoft Azure Compliance Offerings document, or a written confirmation that Azure OpenAI is in scope. That is a short email, not a research task, and it is the right thing to do before the row goes in a proposal.

Read at learn.microsoft.com/en-us/azure/compliance/offerings/offering-hipaa-us and learn.microsoft.com/en-us/compliance/regulatory/offering-hipaa-hitech. Both searched by value for openai, cognitive services and ai foundry: zero matches in each.

Google Cloud, and why it is Gemini Enterprise and not Vertex AI
Confirmed, and corrected
What the vendor says
Google's words: Google enters into Business Associate Agreements as necessary under HIPAA. The Google Cloud BAA covers Google Cloud's entire infrastructure, every region, zone, network path and point of presence, and an enumerated list of products.
Which named service is covered
In the enumerated list: Gemini Enterprise, Gemini Enterprise Agent Platform, Agent Search on Gemini Enterprise Agent Platform, Antigravity in Gemini Enterprise, Gemini Code Assist, Gemini in BigQuery, Gemini in Colab Enterprise and Gemini Notebook Enterprise. All of these sit in the Google Cloud section of the list, not the Workspace section.
The correction
Vertex AI is not on the list. The only entry containing the word Vertex is "Vertex AI Workbench instances", which is the managed notebook, not the model platform. Anything that says "Vertex AI under the Google Cloud BAA" is overstating what Google published. The route here is Gemini Enterprise Agent Platform.
Explicitly excluded
Google's instruction is to disable unsupported Google Cloud services when working with PHI, and in its own words: do not use pre GA offerings with PHI unless expressly noted otherwise. Anything not on the enumerated list is outside the BAA.
Why this route is more interesting than it looks
Anthropic's own documentation says that on Google Cloud's Agent Platform the cloud provider is the data processor. So Gemini Enterprise Agent Platform is a second BAA covered route to Claude, parallel to Bedrock, for a client who is already on Google rather than AWS.

Read at docs.cloud.google.com/docs/security/compliance/hipaa. Google Cloud list last updated 17 September 2025. The product list was searched by value rather than read by eye.

Hathr AI
Confirmed, with one caveat on price
What the vendor says
Hathr's own words: we sign Business Associate Agreements within 24 hours, and a signed BAA is included with the subscription. They run Claude inside AWS GovCloud, an environment they describe as meeting HIPAA and NIST standards.
Prices, from their own page and not a directory
Webapp: 47 dollars a month, described as a single subscription. API: starting at 45 dollars a month, and their API page shows the ladder as 45, then 225, then 700, then 1,200 dollars a month. Enterprise is custom.
The caveat
The 45 dollar figure is a floor, not a price. Their own wording is "starting at", and the next rung is five times it. If Hathr goes in a proposal as the fast start option, it belongs there as a range, because a real workload may not sit on the bottom rung. The webapp figure is written as a single subscription per month rather than per user, so read it as one seat.
Worth knowing
Hathr is a reseller of Claude in a compliant wrapper. The model underneath is the same model as the Anthropic route. What 45 dollars buys is the signature and the environment, not different intelligence.

Read at hathr.ai/pricing and hathr.ai/hipaa-compliant-ai-api.

John Snow Labs
Not confirmed
What the vendor says about a BAA
Nothing. Six of their own pages were searched by value, including the home page, the terms of service, the privacy policy, the software licence agreement, their HIPAA page and their Medical LLM page, well over a megabyte in total. The phrase "business associate" appears zero times on any of them. Their HIPAA page is a technical article about de identification, not a compliance commitment.
Why that is probably not an oversight
What John Snow Labs sells is software you install and run yourself, including on premise and air gapped, with no external API calls. If they never receive PHI, they are not a business associate and no BAA arises in the first place. That puts this row in the same shape as self hosting, not in the same shape as an API vendor who signs.
So the row should read
Not "BAA: yes" as the directories have it, and not "BAA: no" either. Nothing is disclosed to the vendor, so nothing needs to be signed, as long as the deployment is the on premise one. The directory listings that say yes are unsupported at the vendor.
What would settle it
Ask them in writing whether any hosted offering receives PHI, and if so whether they sign a BAA for it. This matters only if CT360 would use a hosted product rather than the libraries.

Searched at johnsnowlabs.com, plus /terms-of-service, /privacy-policy, the libraries licence agreement, /hipaa and /medical-llm. The search was validated against a control string first, so a zero means absent and not blind.

Self hosted Llama, Mistral or Qwen
No BAA needed
Why there is nothing to sign
Nothing is disclosed to a third party, so no business associate exists. The compliance burden moves entirely onto whoever runs the box.
What it costs
A single GPU box running Mistral 7B runs 800 to 1,500 dollars a month. Llama 3 8B on an A10 runs 1,200 to 2,000. These box figures are from industry write ups, not from a vendor page. The 50,000 calls a month break even this page used to carry was a flagship number; computed against the small model this design needs it is between 2.3 and 5.7 million documents a month. The arithmetic is in the prices section below.
The money

The number in the plan is wrong, and it is wrong in a useful direction

The CT360 plan carries about 75 dollars a month for the compliant LLM. That figure does not buy a self hosted model. It is not close: the cheapest self hosted option is ten times it.

But 75 dollars a month is a fair price for a compliant server. The architecture that actually fits is the cheap one: patient data lives on the dedicated box, and the box calls a BAA covered API. The 75 dollars was never the model. It was the room the model is called from.

Do not price self hosting into the first six clinics

It is the most expensive option on this page and it is the one that buys the least. It becomes the right answer at hospital volume and not before.

The prices

What the model actually costs on this workload

The short version, and it is the finding rather than a let down: on the architecture Jeff described, the per token price is close to irrelevant to this deal. The whole model line item lands between 6 and 18 dollars a month, and the two decisions that move it are not which vendor you sign with. They are which model tier you pick and whether you send a cropped page or a whole PDF.

The compliance decision is free. The residency decision costs ten percent

No vendor on this page charges a premium for the BAA, the HIPAA tier or the retention posture. Every vendor that publishes a per token price charges exactly ten percent more to keep inference inside a named geography, and each one says so itself. Those are two separate decisions and they get conflated. A platform owner who adds a United States only requirement late is adding ten percent to every token, not a line item.

The workload, stated so it can be argued with

One safety check per returned document

Jeff's cycle is three steps: map each EMR once through a login, let software read the clinic calendar weekly and build the patient list, then consolidate the record to a PDF and drop it in ShareFile. Nothing in those three steps needs a model to read a patient record. Step two is a query and a date subtraction. Step three is a file move.

The one piece of genuine model work is a safety check that reads page one of a returned PDF to bind the document to the right patient. Everything below prices that, at 30,000 documents a month. These are the assumptions, in the open:

  • A letter sized page scanned at 150 DPI, so 1275 by 1650 pixels.
  • Anthropic and Bedrock: 28 pixel patches, so 46 by 59, which is 2,714 visual tokens. Claude 4.7 and later models allow up to 4,784, so nothing is downscaled.
  • OpenAI and Azure: 32 pixel patches, so 40 by 52, which is 2,080 patches, inside the 2,500 patch budget for detail: high, times the 1.2 model multiplier, which is 2,496 tokens.
  • Google: Google's own stated conversion is 258 tokens per image, and Google prices text, image and video input at the same rate.
  • Add 200 tokens of instruction and 50 tokens of output per document.
  • Sending the whole PDF page instead of a cropped image adds Anthropic's documented 1,500 to 3,000 text tokens per page. The tables use the 2,250 midpoint.

Both numbers in the Nobility file check out, and they tell you what they assumed

That file puts this work at about 80 dollars for 30,000 documents on a small model and 644 on a large one. Against published rates, the 644 is Claude Opus 5.5 reading the whole PDF page at standard routing, which computes to 649.68, within one percent. The 80 is Claude Haiku 5.5 reading the whole PDF page at the rate for prompts over 100,000 tokens, which computes to 81.21, within two percent.

That second one is the useful catch. A one page safety check does not produce a 100,000 token prompt, so the rate that actually applies is the lower one, and the same work costs 16.24 on the whole page or 9.49 on a cropped image. The 80 dollar figure is not wrong arithmetic. It is the right arithmetic at a rate tier this workload never reaches, and it is five to eight times the real number.

Hathr, and what the money buys

The ladder is 45, 225, 700 and 1,200 a month

Read at Hathr's own API page. Base 45, Starter 225, Scale 700, Enterprise 1,200. Asked in volume terms rather than dollars, the honest answer is that the vendor does not say. Across all four rungs the only volume words on the page are higher API rate limits at 700 and discount tokens at 1,200, and neither is quantified. No tokens a month, no request cap, no rate limit number. Two further signs to treat the ladder as indicative and get a quote: the 45 rung lists API access while the 225 rung lists HIPAA compliant API access, and the 1,200 rung says everything in Professional, a tier that does not exist in the ladder.

What the cheap rung buys is the signature and the environment, not better intelligence

Hathr resells Claude from AWS GovCloud and signs a BAA inside 24 hours. It never names a model tier, so you cannot know whether you are buying Haiku or Opus. In a design where the model does almost nothing, that stops being a drawback. If the only model work is one page one check, intelligence is not the thing being purchased. A same day signature and a government hosted environment is, and 45 dollars a month is a fair price for it. At this workload the metered routes cost 6 to 10 dollars, so Hathr's Base rung is roughly four times the metered price and is still the cheapest way to be covered this week rather than this month.

The open question, now answered

The architecture settled the question this page was waiting on

This page previously held the size of the line item open pending one answer: whether the same model would be asked to scrub patient databases for care management triggers. Jeff's three step cycle answers it. No model reads a patient record anywhere in it. The left hand column below is what the design does. The right hand column is the branch that was priced and is not being built, kept because it is the only thing that would change the recommendation.

What the design does

Map each EMR once through a login, with ShareFile mapped. Software reads the clinic calendar weekly and builds the list of patients who are new or not seen in X months. CT360 consolidates the record to a PDF and drops it in ShareFile, and it is filed back to the chart. Mapping prompts carry schema, not patient rows, step two is a query and a date subtraction, and step three is a file move. The one model call is the page one safety check priced above. The compliant LLM is a rounding error and convenience can decide the route.

The branch that is not being built

If a model were asked to read patient records continuously for care management triggers, it would be the centre of the cost and the route would have to be chosen for volume rather than for how fast someone will sign. That is a different recommendation and a different number. Nothing in the three steps requires it, and it is kept here only because it is the single change that would reopen the question.

The precedent is already built. The step three file move exists as roughly 850 lines with one dependency, a browser driver, and no model SDK, no PDF parser and no OCR anywhere in it. A page that priced this work as model work would be pricing the wrong thing.

The recommendation

What to put in front of the platform owner

Anthropic Claude API under HIPAA readiness

In a dedicated organization, called from the dedicated server. Named in the proposal alongside it: AWS Bedrock if a client requires everything inside their own AWS account, and Gemini Enterprise Agent Platform if they are a Google shop, because that reaches the same models under the Google Cloud BAA.

Hathr AI stays on the list as the fast start, at 45 dollars a month and up, if a BAA is needed this week rather than this month. The sign off is same day and that is worth something real.

Leave Azure OpenAI out of the compliance table until Microsoft confirms the service in writing. The BAA is not in doubt. The service being inside it is, and a proposal is the wrong place to find that out.

How to read this page

What was verified, and how

Every claim above was read at the vendor's own compliance page. Where a page could not be read, this page says so rather than filling the gap from a directory listing or a blog.

  • Searched by value, not by eye. Google's product list and Microsoft's compliance pages were pulled as files and searched for the exact strings, because an eight hundred item list is not something to read by scrolling.
  • Every absence was validated against a control first. A search that finds nothing and a search that is broken look identical, so each one was first pointed at a string that does contain what it was hunting for.
  • One gate was measured, not assumed. The Microsoft per service appendix was fetched before being called inaccessible: it returns a sign in page and no document.
  • The OpenAI row is no longer inherited. It was re read at OpenAI's own help centre, which names six eligible products and states that features not listed are not automatically covered. That closing rule is what lets ChatGPT Plus and Team be called excluded rather than merely unmentioned.
  • A price placeholder was not treated as a price. The AWS pricing page ships template tokens, not numbers, so the figures here come from the pricing data file the page itself reads, published the same day. Azure and Google pages were rendered in a browser for the same reason.

A vendor's own page is the only source counted here. Capterra, listicles and vendor directories were the origin of two rows that did not survive contact with the vendor's own words.

Nothing on this page is a compliance opinion and none of it is legal advice. It is a record of what each vendor commits to in writing today, with the page it was read on, so the proposal can cite a source instead of a reputation.
